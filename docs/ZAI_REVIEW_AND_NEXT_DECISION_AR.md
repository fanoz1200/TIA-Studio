# مراجعة ملاحظات Z.AI وخطة القرار التالية

**تاريخ المراجعة:** 24 أغسطس 2026  
**حالة الوثيقة:** قرار تصميم وتشغيل — وليست رأياً قانونياً أو وعداً بنتيجة مطالبة.

> **الخلاصة السريعة:** لا ننقل المشروع أو مصدر الحقيقة إلى أي موقع وكلاء أو نماذج ذكاء اصطناعي. الكود والوثائق والإصدارات تبقى عند المالك في GitHub ونسخة محلية وحزم إصدار محفوظة. نُصلح Windows أولاً، ثم نفصل التعاون المؤقت للفريق عن نسخة التحليل المحلية، ثم نبني مولّد Claim/Narrative ثابتاً بصيغة Word.

## 1. ما الصحيح في كلام Z.AI وما الذي يحتاج تصحيحاً؟

| النقطة | التقييم | القرار الصحيح |
|---|---|---|
| TIA Studio مشروع حقيقي به محرك حساب محلي | صحيح | حسابات CPM/TIA الحتمية يجب أن تظل منفصلة عن الذكاء الاصطناعي. الذكاء الاصطناعي يساعد في الصياغة والمراجعة فقط، لا في اختراع مدد أو علاقات. |
| الكود يحتاج تقسيم `Home.tsx` | صحيح | يعد بند جودة مهم بعد إغلاق مشكلة Windows، لكنه ليس أولوية قبل تشغيل المستخدم للنسخة السليمة. |
| رحلة المستخدم غير منفذة | غير محدث | توجد حالياً رحلة Guided من 8 خطوات، ودليل مصوّر، وبوابة جودة قبل التحليل. يمكن تحسين الربط بالموسوعة لاحقاً، لكن لا نعيد بناء نفس الشغل من الصفر. |
| نسخة Windows Portable 1.0.7 شغالة | غير صحيح في حالة التنزيل الأخيرة | الخطأ الذي ظهر للمستخدم (`Cannot find package 'vite'`) يؤكد أن ملف التنزيل القديم غير صالح للتوزيع. تم إصلاح السبب في المصدر؛ ولا يُعاد توزيعه قبل اختبار حزمة جديدة على Windows حقيقي. |
| ترخيص محلي V1 هو الحل لتجربة الزملاء | غير كافٍ | ترخيص محلي فقط سهل نسخه أو التحايل على التاريخ. يصلح لاحقاً كطبقة راحة، لكنه ليس وسيلة موثوقة لإدارة تجربة فريق محددة المدة. |
| استعمال GitHub بفرع وPull Request | صحيح | هذا هو المسار الوحيد مع أي وكيل خارجي: لا تعديل مباشر على `main`، ولا رفع ملفات العميل الخام أو الأسرار. |

## 2. النسخة التي ظهرت في قائمة Start: ما هي؟

الصورة لا تكفي لتأكيد نوعها بنسبة 100%، لكن وجود أيقونة في قائمة **Start** يعني أنها ليست مجرد ملف Portable عادي في الغالب. الاحتمالان الطبيعيان هما:

| الاحتمال | معناه | كيف تتأكد على جهازك |
|---|---|---|
| **TIA Studio متثبت من Setup قديم** | تطبيق Electron تم تثبيته سابقاً وله اختصار Start وإزالة تثبيت. | افتح `Settings → Apps → Installed apps` وابحث عن **TIA Studio**. أو اضغط كليك يمين على الأيقونة ثم `Open file location`. |
| **PWA متثبتة من Chrome/Edge** | نسخة من واجهة الويب اتثبتت كبرنامج من المتصفح، وقد تعتمد على الإنترنت أو تخزين المتصفح. | من خصائص الاختصار راجع المسار؛ لو شغل `chrome.exe` أو `msedge.exe` فهي PWA وليست حزمة Electron المحلية. |

لا ننصح باعتبارها إصداراً معتمداً لمجرد أنها تفتح. يلزم معرفة المسار والإصدار أولاً، لأن النسخة الظاهرة في الصورة قد تكون قديمة أو مرتبطة بواجهة ويب مخزنة مؤقتاً.

## 3. لماذا ملف Windows الأخير فشل؟ وما الذي تغير؟

رسالة الخطأ تقول إن التطبيق شغّل خادم البرنامج من مجلد مؤقت بعد فك الضغط، ثم حاول استيراد `vite` وقت التشغيل. `vite` أداة تطوير وليست جزءاً يجب أن يعتمد عليه برنامج Windows الإنتاجي.

الإصلاح الجاري فصل خادم الإنتاج الثابت عن مسار التطوير، بحيث لا يستورد `vite` في حزمة Electron. تم بناء نسخة Portable مصححة والتحقق منها في بيئة Windows معزولة. كما أُضيف مسار **Setup** حقيقي حتى لا يختلط التثبيت بالتشغيل المباشر.

> **حالة الاعتماد:** لا يوزع أي ملف جديد على الفريق قبل اختبار التثبيت والتشغيل على جهاز Windows حقيقي. اختبار Wine مفيد لاكتشاف أخطاء التغليف، لكنه لا يثبت توافق SmartScreen أو كل سلوك Windows الفعلي.

### التسميات التي نعتمدها بعد الإصلاح

| الملف | وظيفته | لمن يناسب |
|---|---|---|
| `TIA-Studio-1.0.7.1-Setup.exe` | مثبت Windows حقيقي؛ ينشئ اختصار Start وخيار إزالة تثبيت. | المستخدم العادي والجهاز الشخصي أو جهاز الفريق. |
| `TIA-Studio-1.0.7.1-Portable.exe` | تشغيل مباشر من مجلد يختاره المستخدم، بلا تثبيت ولا Start تلقائياً. | فحص سريع أو جهاز لا يسمح بالتثبيت. |
| `TIA-Studio-1.0.7.1-Source.tar.gz` | مصدر البرنامج وتعليمات البناء. | المالك أو المطور البديل فقط. |

الرقم `1.0.7.1` مقصود كـ **Hotfix** لمشكلة Windows؛ لا نسمّي الملف الجديد 1.0.7 نفسه حتى لا يختلط بالملف المعطوب الذي وصل للمستخدم.

## 4. هل تسجيل الدخول مهم إذا كان التحليل محلياً؟

### عند استعمال البرنامج محلياً على جهاز واحد

لا يحتاج المستخدم إلى تسجيل دخول لكي يقرأ XER أو يملأ الوقائع أو يشغّل الحساب المحلي. تسجيل الدخول لا يجعل حسابات CPM/TIA أدق، ولا ينبغي أن يكون شرطاً لتحليل ملفات مشروع العميل على جهازك.

### عند العمل مع زملاء أو تجربة محددة المدة

هنا تسجيل الدخول يصبح مفيداً، لكن **في مساحة عمل مشتركة على الويب** وليس داخل ملف EXE وحده:

| الحاجة | الحل الصحيح | لماذا |
|---|---|---|
| دعوة زميل لمدة 14 أو 30 يوماً | عضوية Team Workspace لها تاريخ انتهاء على الخادم | يمكن إلغاء الوصول فعلياً حتى لو احتفظ الزميل بالرابط. |
| صلاحية مدقق فقط | Role مثل `Reviewer` مع قراءة وتعليقات دون تصدير أو تعديل | يحد من تعديل الحسابات أو الأدلة. |
| سجل من عدّل ماذا ومتى | Audit log على الخادم | مفيد للمراجعة الداخلية، لا يمثل إثباتاً قانونياً منفرداً. |
| ملفات XER/XLSX حساسة | تحفظ محلياً أو في مساحة S3 خاصة مرخصة؛ لا تُرفع إلى GitHub | لا تخرج بيانات العميل إلى مستودع عام أو موقع وكيل خارجي. |

**القرار المقترح:** نجعل برنامج سطح المكتب "TIA Analyst" محلياً ومفتوحاً لصاحب النسخة، ونبني لاحقاً "TIA Team Workspace" للدعوات المؤقتة. لا نبدأ الآن بترخيص محلي ضعيف ثم نبني كل النظام مرة ثانية.

## 5. حماية المشروع من تغير أي منصة أو موديل

التجربة السابقة مع Z.AI صحيحة كمخاطرة تشغيل. العلاج ليس انتظار المنصة؛ العلاج أن تكون كل أصول المشروع عند المالك دائماً.

### قاعدة المصدر الواحد

1. مستودع GitHub هو النسخة المشتركة للكود، ويفضل تحويله إلى **Private** قبل إضافة أي ملفات غير عامة.
2. نسخة محلية على جهاز المالك أو قرص خارجي: `git clone` للمستودع + مجلد `releases` لحزم Windows + مجلد `handover` للوثائق.
3. كل تغيير يأتي من وكيل أو مطور في فرع مستقل، ثم Pull Request ومراجعة واختبارات قبل الدمج في `main`.
4. لا توضع أسرار، مفاتيح API، قواعد بيانات، XER/XLSX العميل، أو مراسلات المشروع في Git أو في prompt لموقع خارجي.
5. كل إصدار له: رقم نسخة، `SHA-256` للحزمة، ملاحظات إصدار، وسجل اختبار مختصر.

### حزمة الاستمرارية التي يجب أن تظل عندك

| المجلد أو الملف | المحتوى |
|---|---|
| `source/` | clone كامل للمستودع، بما في ذلك `package.json` و`pnpm-lock.yaml`. |
| `releases/` | Setup وPortable وSource لكل إصدار مع SHA-256. |
| `docs/PROJECT_HANDOVER.md` | كيف تُشغّل، تختبر، تبني، وتنشر التطبيق، وأين توجد الحدود المعروفة. |
| `docs/ARCHITECTURE.md` | خريطة المحركات: الاستيراد، CPM/TIA، التقرير، سطح المكتب، الويب. |
| `docs/DECISIONS.md` | قرارات المنتج وتاريخها؛ مثل فصل Desktop عن Team Workspace. |
| `client-data/` خارج Git | ملفات العميل الخام والأدلة. لا تُرسل لوكيل أو إلى مستودع عام إلا بموافقة صريحة. |

### كيف يتعامل Z.AI أو أي وكيل خارجي مع المشروع؟

يعطى نسخة من GitHub أو ZIP مصدر خالٍ من بيانات العميل، ويعمل فقط في فرع مثل `feature/claim-document-v1`. لا نستخدم مجلد مشروع مخفي داخل منصة الوكيل كمصدر وحيد. قبل تسليم أي شغل يقدّم الوكيل: diff، اختبارات، تعليمات تشغيل، وتغييراً واحداً واضحاً لكل Pull Request.

## 6. مولّد Delay Analysis Narrative وFull Claim: الشكل الصحيح

المطلوب منطقي ومفيد، لكن لا ينبغي أن يكون "برومبت ضخم" يبتلع كل بيانات المشروع ويطبع مستنداً غير قابل للتتبع. الحل الاحترافي هو **قالب Word ثابت + حزمة حقائق منظمة + مراجعة بشرية**.

### مخرجات النظام

1. **Delay Analysis Narrative**: تقرير فني يشرح البرنامج والمنهجية والوقائع ونتائج TIA، مرتبط بجدول الأدلة والرسومات.
2. **Full Claim Draft**: مستند أكبر، يضم الـNarrative كقسم فني مع هيكل مطالبة قابل للتعديل.
3. **Evidence Index**: فهرس للأدلة، مصدر كل واقعة، حالة المراجعة، وما ينقص.
4. **Reconciliation Manifest**: ملف يربط كل رقم أو رسم في التقرير بمدخلات التحليل وبصمة التشغيل، لمنع خلط النتائج.

### هيكل ثابت لملف Word

| الباب | ما يملؤه النظام | ما يحتاج مراجعة المالك/المستشار |
|---|---|---|
| الغلاف والتحكم في المستند | اسم المشروع، رقم التقرير، المراجعة، التاريخ، شعار اختياري | الاسم الرسمي، شعارات العميل، رقم العقد. |
| فهرس المحتويات | ينشأ تلقائياً من عناوين Word | تحديث الحقول داخل Word عند التعديل النهائي. |
| الملخص التنفيذي | ملخص من نتائج TIA والوقائع المعتمدة | صياغة التوصية النهائية. |
| خلفية المشروع ونطاق التكليف | حقول مشروع منظمة | بيانات العقد والنطاق الفعلي. |
| المستندات والأدلة | Evidence Index | إضافة مستندات أو مراجع لم تُرفع. |
| المنهجية والاختبارات | تعريف TIA، نافذة التحليل، بوابة الجودة، حدود المحرك | اعتماد المنهجية وتطبيقها على العقد. |
| وقائع التأخير | سجل الوقائع، المسؤولية الظاهرة، السبب، التواريخ | إثبات السبب والتبعات والتزامن. |
| التحليل الزمني | جداول CPM/TIA والـFragnet والتواريخ وGantt | مراجعة Primavera العكسية عند الحاجة. |
| الإشعارات والاتصالات | مسودات Notices وسجل المراسلات | الاعتماد القانوني والإرسال الفعلي. |
| الأثر المالي والكمّي | جداول مدخلات وحقول ناقصة | أسعار، تكلفة، إثبات محاسبي، ضريبة. |
| الاستنتاج والمطلوب | مسودة مبنية على البيانات المعتمدة | القرار القانوني والاستحقاق النهائي. |
| الملاحق | Excel، الرسومات، بصمات الملفات، الجداول | أي ملحقات تعاقدية أو أدلة أصلية. |

> لا ينتج البرنامج حكماً قانونياً أو حق تمديد/تعويض تلقائياً. التقرير يميز دائماً بين **بيانات مثبتة**، و**تحليل فني**، و**نص يحتاج مراجعة**، و**معلومة ناقصة**.

### دور الذكاء الاصطناعي — اختياري وتحت السيطرة

الذكاء الاصطناعي لا يكتب المستند من الصفر. النظام أولاً ينشئ `Claim Fact Pack` منظمًا (JSON/HTML/PDF): أرقام، وقائع، جداول، مراجع الأدلة، مواضع النقص، ورسومات. بعدها يمكن تشغيل الذكاء الاصطناعي على كل قسم منفصل لإنتاج **مسودة**، مع الإشارة إلى أرقام الوقائع والأدلة التي استند لها.

لا نرسل العقد أو المراسلات أو ملف XER الخام إلى DeepSeek أو Qwen أو Z.AI من دون مراجعة سرية وموافقة المالك. لو اُستخدم نموذج خارجي، نرسله نسخة منزوعة البيانات الحساسة قدر الإمكان، وتبقى النتيجة مسودة يراجعها شخص مختص.

| الأولوية | العمل | سبب الترتيب | مخرج واضح |
|---|---|---|---|
| P0 | اعتماد إصلاح Windows على جهاز Windows حقيقي | لا يجوز توزيع ملف فشل بالفعل. | `Setup` و`Portable` باسم 1.0.7.1 + اختبار تشغيل موثق. |
| P1 | حزمة الاستمرارية والـHandover | تحميك من تغير أي منصة قبل توسيع النطاق. | مصدر محلي، GitHub منظم، وثائق بناء وإصدار. |
| P2 | Team Workspace بدعوات منتهية | يحل تجربة الفريق بصورة حقيقية. | Invite + expiry + role + audit log على الويب. |
| P3 | Claim/Narrative Word Template V1 | يقدم المخرج المهني الذي تحتاجه بعد التحليل. | ملف DOCX ثابت قابل للتحرير + Evidence Index. |
| P4 | ربط أعمق بين الموسوعة والرحلة وتقسيم `Home.tsx` | تحسين قابلية الاستعمال والصيانة. | خريطة انتقال واضحة ومكونات أصغر. |
| P5 | فيديوهات وميزات ثانوية | مؤجلة بطلب المالك. | نصوص/فيديوهات عند توفر أداة مناسبة. |

## 8. قرارات لا تحتاج انتظاراً

1. **لا نعيد بناء رحلة 9 خطوات من الصفر.** نحسن الرحلة الحالية ونربطها بالموسوعة لأن الجزء الأساسي منفذ فعلاً.
2. **لا نوزع ملف Windows القديم الذي ظهر فيه خطأ Vite.** نزيله من مركز التنزيل فور اعتماد 1.0.7.1.
3. **لا نستخدم ترخيصاً محلياً فقط كتأمين على تجربة الفريق.** الوصول المؤقت يحتاج تحققاً من الخادم.
4. **لا نعتمد على أي منصة كنسخة وحيدة للمشروع.** GitHub + نسخة محلية + حزمة مصدر + releases هي القاعدة.
5. **لا نستخدم برومبت واحداً عملاقاً لإنتاج Claim.** نستخدم قالب DOCX ثابتاً وFact Pack واضحاً ومرحلة مراجعة.

## 9. نقطة تحتاج قرار المالك لاحقاً

عندما يكون Windows 1.0.7.1 جاهزاً للاختبار الحقيقي، يحدد المالك فقط: هل فريقه يحتاج أولاً **مساحة عمل مشتركة على الويب بدعوات مؤقتة** أم نبدأ مباشرة بـ **مولّد Word للـNarrative والـClaim**؟ يمكن تنفيذ المسارين، لكن تنفيذهما بالتتابع يقلل المخاطر ويعطي نتائج قابلة للاختبار.
