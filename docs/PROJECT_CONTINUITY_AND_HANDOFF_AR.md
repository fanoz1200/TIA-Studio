# دليل استمرارية وتسليم مشروع TIA Studio

**الحالة:** مرجع تشغيلي حيّ. يجب تحديثه مع كل تعديل يؤثر في المحرك أو التوزيع أو البنية.

## الهدف

هذا الملف يضمن أن مشروع **TIA Studio** لا يعتمد على جلسة عمل واحدة أو على جهاز واحد. يستطيع أي مطور أو وكيل لاحق فتح نفس المصدر، تشغيل الاختبارات، رؤية نفس الواجهة، ومتابعة البناء من آخر نقطة محفوظة بدلاً من إعادة المشروع من الصفر.

> المصدر البرمجي هو الأصل المرجعي. حزمة Windows أو Linux هي ناتج تشغيل للمستخدم النهائي وليست بديلاً عن المصدر أو تاريخ التعديلات.

## أين تُحفظ الأشياء

| الأصل | المكان المرجعي | ما الذي يُحفظ معه | ما الذي لا يوضع معه |
|---|---|---|---|
| كود المشروع وتاريخه | مستودع Git خاص يملكه المستخدم | المصدر، الاختبارات، التوثيق، أمثلة التدريب، الإعدادات غير السرية | كلمات المرور وملفات `.env` وحزم Electron الكبيرة |
| نسخة احتياطية قابلة للنقل | ملف ZIP مصدر لكل إصدار مهم | صورة نظيفة من المصدر مع هذا الدليل | `node_modules` و`release` و`dist` والسجلات |
| نسخة المستخدم النهائي | ملف EXE واحد لـ Windows أو AppImage واحد لـ Linux | رقم الإصدار وتعليمات التشغيل | مصدر التطوير أو أسرار البيئة |
| ملفات المستخدم والمشروعات | جهاز المستخدم أو مساحة تخزين يختارها المستخدم | XER/XML وExcel والأدلة والتقارير | لا تُرفع تلقائياً إلى المصدر أو إلى Git |

## الاختيار الموصى به

استخدم **مستودع Git خاص يملكه المستخدم** كمصدر وحيد للحقيقة، مع الاحتفاظ بنسخة ZIP محلية في جهازك في نهاية كل إصدار مهم. هذا أفضل من تنزيل كل الملفات يدوياً في كل جلسة، لأنه يحافظ على تاريخ التغييرات، ويجعل مقارنة الإصدارات والرجوع لإصدار سابق واضحة.

إذا لم ترغب في استخدام Git حالياً، احتفظ بملف ZIP المصدر المرفق بكل إصدار في مجلد ثابت على جهازك أو في مساحة تخزين سحابية خاصة. يستطيع أي وكيل جديد البدء من هذا الملف، لكنه لن يرى تاريخ التعديلات التفصيلي إلا إذا احتفظت أيضاً بملف Git bundle أو بمستودع Git.

## تسليم المشروع إلى مطور أو وكيل جديد

أعطِ الشخص أو الوكيل الجديد **المستودع الخاص** أو **ملف ZIP المصدر**، ثم اطلب منه قراءة الملفات التالية قبل أي تعديل:

| أولوية القراءة | الملف | الغرض |
|---:|---|---|
| 1 | `README.md` و`package.json` | معرفة حزم المشروع وأوامر التشغيل والبناء |
| 2 | `todo.md` | معرفة المكتمل، المفتوح، والعناصر التي تنتظر مصادر فعلية |
| 3 | `docs/TIA_STUDIO_LIVE_GUIDE_AR.md` | فهم رحلة المستخدم والمنهجيات والمحركات |
| 4 | `docs/PROJECT_CONTINUITY_AND_HANDOFF_AR.md` | فهم قواعد الاستمرارية والتسليم |
| 5 | `client/src/lib/cpm.ts` و`client/src/lib/workflow-validation.ts` | فهم محرك CPM/TIA وبوابات القبول قبل التصدير |
| 6 | `client/src/pages/Home.tsx` و`client/src/components/` | فهم الواجهة والتبويبات وتدفق العمل |

بعد ذلك يشغّل الوكيل الجديد الأوامر التالية من جذر المشروع:

```bash
pnpm install
pnpm test
pnpm build
pnpm dev
```

إذا نجحت الاختبارات والبناء، فهو يعمل فوق **نفس التطبيق** والمنطق والواجهة. لا يحتاج إلى بنائه من جديد؛ أي تغيير جديد يجب أن يكون تعديلًا فوق المصدر نفسه مع اختبار وانشاء إصدار جديد.

## الحدود التي يجب أن يعرفها من يتسلم المشروع

| المجال | ما الذي ينتقل كما هو | ما الذي قد يحتاج إعداداً جديداً |
|---|---|---|
| التحليل المحلي | محرك CPM/TIA، مشاريع التدريب، الفحوصات، التقارير، Excel وXER التجريبي | لا شيء لتطوير منطق المتصفح |
| سطح المكتب | مصدر Electron، إعدادات البناء، دليل التشغيل، الاختبارات | إعادة بناء الحزمة على بيئة التطوير المناسبة واختبارها على Windows أو Linux |
| قاعدة البيانات وتسجيل الدخول | المصدر وتعريفات الواجهة والخادم | إعداد بديل لقاعدة البيانات، OAuth، التخزين والأسرار عند تشغيله خارج البيئة الحالية |
| روابط التنزيل | أسماء الحزم وتعليمات الإصدار | إعادة رفع الأصول إلى التخزين الخاص بالمالك عند الانتقال لمنصة أخرى |

لا تُنسخ ملفات الأسرار أو ملفات البيئة إلى Git أو إلى ZIP العام. عند الانتقال إلى جهة استضافة أو بيئة جديدة، يضبط المالك الأسرار وقاعدة البيانات في تلك الجهة، ثم يشغّل الوكيل الاختبارات مرة أخرى قبل النشر.

## قاعدة الإصدار في نهاية كل جلسة

1. تُحدّث بنود `todo.md` بالبنود المكتملة والمفتوحة دون حذف التاريخ.
2. تُشغّل `pnpm test` و`pnpm build`.
3. إذا تغير تطبيق سطح المكتب، تُبنى حزمة Windows وحزمة Linux ويُختبر مسار الإقلاع. تتضمن بيئة Linux المزودة بـ Wine وXvfb الأمر `pnpm desktop:verify:windows-sandbox` لتشغيل ملف EXE في ملف مستخدم مؤقت ورصد الخادم المحلي.
4. يُحدَّث الدليل الحيّ وسجل التغييرات ورقم الإصدار عند وجود تغيير مؤثر على المستخدم.
5. يُنشأ إصدار محفوظ، ثم يُصدّر ملف ZIP مصدر نظيف و/أو Git bundle للإصدار.
6. يُعطى المستخدم رابط النسخة التنفيذية وتعليمات تشغيلها، مع رابط حزمة المصدر.

## فحص سريع قبل قبول أي تعديل

> لا تقبل تغييراً في محرك التحليل أو استيراد P6 أو التصدير أو الحزمة المحلية لمجرد أن الواجهة تبدو سليمة.

يجب أن يحقق التعديل ما يأتي: نجاح الاختبارات، نجاح بناء الإنتاج، عدم تعديل ملف P6 الأصلي، استمرار بوابة جودة الجدول وبوابة منع التصدير، ظهور التغيير في الدليل الحيّ عند تأثيره على المستخدم، وحفظ إصدار قابل للرجوع إليه.
