# منهجية وخطة Half–Zero Step Analysis قبل التنفيذ

> **حالة الوثيقة:** خطة ومنهجية فقط. لا تضيف هذه الوثيقة محركاً أو زراراً أو نتيجة تحليل جديدة في TIA Studio، ولا تصدر قرار تمديد مدة (EOT) أو مسؤولية أو entitlement.

**المؤلف:** Manus AI  
**تاريخ الإعداد:** 26 أغسطس 2026  
**الغرض:** وضع معيار مهني قابل للمراجعة قبل البدء في بناء تحليل Half-Step وZero-Step.

## 1. القرار التصميمي

سيُبنى التحليل—بعد موافقة المستخدم على هذه الخطة—كموديول واحد باسم **Update-to-Update Split / Half–Zero Step Analysis**، وليس كزرارين منفصلين. فالـHalf-Step هو المسار التشغيلي الرئيسي الذي يفصل أثر التقدم المسجل عن أثر revisions في الخطة بين تحديثين متتاليين. أما الـZero-Step فهو حالة تحكم مكملة للتحقق من حساسية التقسيم وتوثيق أثر revisions من اتجاه مختلف؛ لا يعد نتيجة مستقلة أو دليلاً تعاقدياً بذاته.[1] [2]

| المكوّن | وظيفته المهنية | ما لن يفعله |
|---|---|---|
| Readiness Gate | يقرر هل زوج التحديثات صالح للتحليل أو يحتاج مراجعة | لا «يصلح» ملف P6 أو يفترض بيانات غائبة |
| Change Register | يسجل التغييرات المصنفة ومصدرها | لا ينسب مسؤولية قانونية للتغيير |
| Half-Step | يعزل أثر progress بين تحديثين | لا يثبت EOT أو entitlement تلقائياً |
| Zero-Step | فحص تحكم وحساسية لمسار تقسيم revisions/progress | لا يزيل حكم المحلل أو أدلة الموقع |
| Reconciliation | يثبت أن الأثر التفصيلي يطابق حركة النهاية ضمن دقة معلنة | لا يخفي residual أو interaction غير مفسر |

## 2. نطاق التحليل وحالات الجدول

يراجع التحليل زوجاً متتالياً من التحديثات لنفس المشروع أو لمجموعة موثقة من خرائط Activity ID. يلزم أن يكون لكل تحديث Data Date معروف، وأن يكون ترتيب التحديثات زمنياً. تصف مراجع Half-Step العملية بأنها فصل progress reporting عن non-progress revisions ثم إعادة حساب الجدول عند Data Date التحديث التالي؛ وتذكر صراحةً أن additions/deletions والمنطق والـlags والقيود والمدد والتقاويم من تغيرات يجب أن تظهر وتراجع، لا أن تختفي داخل النتيجة.[2] [3]

| الرمز | الحالة | تعريفها العملي |
|---|---|---|
| **A / Previous** | خطة A + تقدم A | آخر تحديث معتمد قبل نافذة المقارنة |
| **H / Half-Step** | خطة A + تقدم B | نسخة وسيطة: تنقل تغييرات progress المصنفة من B إلى هيكل A، ثم تعاد الجدولة عند Data Date B |
| **Z / Zero-Step** | خطة B + تقدم A | نسخة تحكم: تستبدل هيكل الخطة بتغييرات B مع إبقاء progress A حيثما أمكن وبشكل معلن |
| **B / Current** | خطة B + تقدم B | التحديث الحالي كما ورد، بعد فحوص الاستيراد |

المقصود بـ«الخطة» هنا هو العناصر غير المصنفة progress: هيكل الأنشطة، العلاقات، lags، القيود، calendars، ومنطق مدة العمل أو النطاق حسب تصنيف change register. والمقصود بـ«التقدم» هو actual starts/finishes، نسب الإنجاز/الكميات حيث يتاح دعمها، وحالة النشاط وتاريخها. لا تُصنّف Remaining Duration تلقائياً؛ بل تسجل كـprogress أو revision أو **needs analyst review** وفق دليل التحديث وقواعد متفق عليها.

## 3. معادلات النتيجة والتسوية

ليكن `F(S)` تاريخ النهاية أو milestone الهدف بعد إعادة حساب الحالة `S` وفق تقويمها وقيودها الموثقة، ولتكن الإشارات الموجبة تأخيراً بالنسبة للهدف.

| القياس | المعادلة | التفسير |
|---|---|---|
| الحركة الصافية | `ΔNet = F(B) − F(A)` | تغير نهاية المشروع/المعلم بين التحديثين |
| أثر التقدم في مسار Half | `ΔProgress(H) = F(H) − F(A)` | الحركة بعد نقل progress فقط إلى خطة A |
| أثر revisions في مسار Half | `ΔRevision(H) = F(B) − F(H)` | الحركة المتبقية بعد الوصول إلى H |
| تسوية مسار Half | `ΔNet = ΔProgress(H) + ΔRevision(H)` | شرط حسابي ظاهر في التقرير |
| فحص مسار Zero | `ΔRevision(Z) = F(Z) − F(A)` و`ΔProgress(Z) = F(B) − F(Z)` | فحص مسار بديل؛ مجموعهما يجب أن يعيد `ΔNet` |

لا يلزم أن تتساوى قيمة `ΔProgress(H)` مع `ΔProgress(Z)` أو قيمة revisions في المسارين. إذا تفاعلت التغييرات مع بعضها، يصبح توزيع الأثر **path-dependent**. يعرض البرنامج وقتها فرق المسارين كـ**interaction / sensitivity note**، لا يختار رقماً سراً ولا ينسبه إلى طرف. وينبغي معالجة progress على وحدات تخطيط مناسبة—عادة يومياً حيث تسمح البيانات—لأن ترتيب دفعة واحدة من تغييرات متزامنة قد يحجب concurrency أو يغير قراءة الأثر.[1] [4]

## 4. بوابة جاهزية بيانات P6/XER

لا يعمل التحليل كآلة «قبول» لكل ملف. قبل تشغيل أي حالة، تصدر البوابة نتيجة **Ready** أو **Ready with analyst review** أو **Blocked** وتحتفظ بسببها.

| الفحص | Ready | Blocked / يحتاج مراجعة |
|---|---|---|
| هوية الجدول | project identity وActivity IDs قابلة للمطابقة أو mapping مصرح | مشروع مختلف بلا mapping، IDs مكررة أو تغيير غير موثق واسع |
| الترتيب الزمني | Data Date لـB بعد A، ولا يوجد تعارض في snapshot | Data Date غائب أو متساوٍ/راجع أو غير قابل للقراءة |
| حالة التقدم | actual starts/finishes والحالة قابلة للتفسير | progress ناقص جوهرياً أو تواريخ مخالفة بلا تفسير |
| منطق الجدول | relationships/lag/calendar/constraints مستوردة ومفحوصة | فشل استيراد أو عناصر لا يدعمها المحرك بلا disclosure |
| تغييرات النطاق | added/deleted/split/combined activities مسجلة | تغيير واسع بلا Activity ID mapping أو سجل تغيير |
| القيود والتقاويم | فرق القيود والتقاويم والعطلات ظاهر في register | calendar definition مفقود أو constraint غير مقروء |
| الهدف | project finish أو milestone محدد ومبرر | لا هدف زمني محدد أو الهدف غير قابل لإعادة الحساب |

## 5. التصنيف المطلوب للتغييرات

تسجل كل مقارنة في **Change Register** قابل للفرز والتصدير. لا يعتبر السجل دليلاً سببياً؛ هو دليل تقني على ما اختلف بين النسختين.

| فئة التغيير | أمثلة | المعالجة المبدئية |
|---|---|---|
| Progress | actual start/finish، حالة النشاط، completion | ينقل إلى H وفق تاريخ progress ووحدة المعالجة |
| Logic | predecessor/successor، relationship type، lag | revision ظاهر؛ لا ينقل إلى H إلا بتصنيف محلل مسبب |
| Duration | Original/Remaining Duration | يصنف بعد قواعد صريحة ودليل update؛ لا افتراض تلقائي |
| Calendar | calendar assignment، workweek، holidays | revision ظاهر مع حساب أثره إن أمكن |
| Constraint | type/date/weight of constraint | revision ظاهر وتحذير خاص إن كان hard constraint |
| Scope/identity | added/deleted/split/merged activities | mapping أو استثناء مسبب؛ قد يمنع التحليل |
| Unknown | عنصر مستورد لا يتوفر له تفسير أو دعم | لا يدخل allocation؛ يظهر كـblocker أو residual |

## 6. مخرجات الإصدار الأول المقترح

المخرج ليس «قرار مطالبة». هو ملف تقني ومراجعة داخل التطبيق يمكن للمحلل اختيار إدراج جزء منه في Delay Analysis Narrative أو Claim بعد تحريره.

| المخرج | المحتوى |
|---|---|
| Readiness Report | حالة كل فحص، التحذيرات، النسخ المستخدمة، target والمحلل المسؤول عن المراجعة |
| Window Overview | A/H/Z/B، Data Dates، حركة النهاية، progress/revision، residual وفرق المسارين |
| Change Register | التغييرات، تصنيفها، تاريخها إن وجد، أثرها/عدم أثرها، دليلها وملاحظة المحلل |
| Target Detail | longest/critical path والميلستون المستهدف في كل حالة مع disclosure للقيود |
| Concurrency Note | التغييرات المتزامنة وطريقة معالجة وحدة التخطيط وحدود القراءة |
| Narrative Draft | فقرة فنية قابلة للتعديل والنسخ؛ لا تتضمن تلقائياً مسؤولية أو EOT أو مبلغ |

## 7. خطة الاختبار ومعايير القبول

ينفذ الاختبار قبل إدخال ملفات مشروع العميل. تستخدم البداية schedules صناعية صغيرة ومعلومة النتيجة، ثم ملفات P6 متتابعة يختارها المستخدم وتتم مقارنتها في Primavera P6. لا تُرفع ملفات العميل أو أدلته لخدمة خارجية؛ تظل المعالجة محلية ضمن التطبيق/جهاز المستخدم حيثما تكون الميزة محلية.

| حالة الاختبار | ما يجب إثباته |
|---|---|
| Progress فقط | `F(A) → F(H)` يفسر كل الحركة و`H = B` هيكلياً |
| Logic revision فقط | progress effect صفر أو معلن، والأثر ظاهر بين `H → B` |
| Calendar/holiday revision | التغيير ظاهر في register وبآثار قابلة لإعادة الحساب |
| Remaining duration متنازع عليها | لا تصنف تلقائياً؛ يتوقف allocation أو يطلب مراجعة |
| Added/deleted activities | mapping أو blocker واضح ولا فقدان صامت للنطاق |
| Out-of-sequence progress | يظهر كتحذير وتصنيف قابل للمراجعة |
| Concurrent changes | معالجة بوحدة زمنية معلنة، وإظهار shared/sensitivity عند اللزوم |
| P6 parity | توثيق مقارنة تواريخ الهدف والمسار/القيود في P6 مع سبب أي فرق |

لا يعلن الإصدار «جاهزاً للاستخدام المهني» إلا إذا تحققت المعايير التالية: (1) كل زوج تحديثات يملك Readiness Result محفوظاً، (2) تسوية Half وZero مرئية ضمن دقة معلنة، (3) لا تُخفى unknown changes أو residual، (4) تمر الحالات الصناعية، (5) تتم مطابقة حالة أو أكثر في Primavera P6، و(6) يظل لكل استنتاج قابل للتعديل والتحفظ من المحلل.

## 8. مراحل التنفيذ بعد الموافقة

| المرحلة | ساعات العمل التقديرية | نقطة الموافقة |
|---|---:|---|
| تثبيت منهجية/تصنيف/Ready Gate | 8–12 | اعتماد الوثيقة وقواعد التصنيف |
| نموذج بيانات ومقارنات snapshots | 8–14 | مراجعة change register على أمثلة صناعية |
| محرك Half/Zero وإعادة الحساب والتسوية | 30–45 | مقارنة نتائج مرجعية وشفافية residual |
| واجهة ومخرجات قابلة للمراجعة | 12–18 | مراجعة رحلة المستخدم ونص المسودة |
| اختبارات، P6 parity، QA | 20–30 | قبول/رفض الإصدار التجريبي على ملفات متتابعة |
| **الإجمالي** | **78–119** | لا يبدأ التنفيذ قبل الموافقة على هذه الخطة |

## 9. ما يلزم من المستخدم لاحقاً—not now

عند اعتماد بدء التنفيذ فقط، يلزم زوجان أو أكثر من updates متتالية من نفس المشروع، مع معرفة أي Update هو المعتمد، وData Date لكل نسخة، والميلستون/نهاية المشروع المطلوب قياسها. إذا وُجد سجل تغييرات أو ملاحظات تحديث أو baseline reference، يوثق محلياً كمصدر مراجعة. لا يلزم إرسال بيانات العميل لخدمة خارجية.
