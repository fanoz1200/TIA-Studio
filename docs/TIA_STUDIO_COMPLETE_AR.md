# دليل TIA Studio التقني الكامل

> **الغرض من هذا الدليل:** شرح ما بُني في التطبيق، ولماذا بُني بهذه الطريقة، وكيف يمكن لفريق تقني إعادة بنائه أو تطويره مع الحفاظ على قابلية تتبع تحليل التأخير. هذا الدليل يصف النسخة الحالية ولا يحول نتائج البرنامج إلى رأي قانوني أو قرار استحقاق.

## 1. بطاقة المنتج ونطاقه

**TIA Studio** هو مساحة عمل عربية لتحليل التأخير الإنشائي. يستقبل برنامجاً زمنياً، يبني شبكة CPM، يدرج حدثاً في صورة Fragnet، ثم يقارن قبل/بعد الحدث لإظهار أثره المحتمل على تاريخ الإكمال. توسعت النسخة الحالية لتحتفظ بإسنادات موارد وتكاليف P6، وسجل Notices، ومسار اعتماد إلكتروني، وتقرير مطالبة عربي قابل للتصدير.

| البند | ما يفعله التطبيق حالياً | ما لا يدعيه التطبيق |
|---|---|---|
| التحليل الزمني | CPM وTIA ونوافذ تحليل وفحص تزامن وسرد فني | إثبات الاستحقاق التعاقدي وحده |
| P6 | استيراد XER وPrimavera XML، WBS، نسب إنجاز، تقاويم، وعلاقات | اعتماد أن ملف P6 صحيح أو معتمد تعاقدياً |
| التكاليف | تقدير تعرض تكلفة تشغيلي من إسنادات المورد في نطاق الحدث | تسعير مطالبة نهائي أو فائدة أو تعويض قانوني |
| Notices | مسودة وسجل ومواعيد وأدلة مرجعية | إرسال Notice بالنيابة عن الشركة |
| الاعتماد | مراحل مراجعة، تعيين مراجعين، وسجل تدقيق | استبدال تفويض المؤسسة أو توقيعها الرسمي |

## 2. المبدأ العلمي الذي يحكم التطبيق

يعامل التطبيق **البرنامج المرجعي، والتقويم، ومنطق العلاقات، والحدث، والأدلة** كسلسلة واحدة قابلة للمراجعة. لا يكفي أن يظهر الفرق في تاريخ الإكمال؛ بل يلزم أن يستطيع المراجع الرجوع إلى النشاط والعلاقة المستبدلة وبيانات المورد والقرار المسجل. هذا يتفق مع غرض Time Impact Analysis بوصفه اختبار أثر إدراج حدث في شبكة برنامج محددة، مع ضرورة التحقق من صلاحية البرنامج والتقويم والمنطق قبل قراءة النتيجة [1] [2].

> **قاعدة تشغيلية:** أي نتيجة «أيام تمديد» هي مخرَج نموذج زمني مبني على مدخلات محددة. إذا تغيّرت نسخة البرنامج أو التقويم أو العلاقات أو نطاق الـ Fragnet، وجب إعادة الحساب وحفظ النسخة الجديدة.

## 3. البنية المعمارية

التطبيق مبني كواجهة React/TypeScript مع خادم Express وواجهات tRPC وقاعدة MySQL/TiDB عبر Drizzle ORM. يحتفظ المتصفح بحالة التحليل اليومية محلياً كي تكون الحسابات سريعة، بينما تحفظ السجلات التي تتطلب تتبعاً أو مشاركة ضمن الحساب المسجّل عبر الخادم.

```text
P6 XER / P6 XML / JSON / CSV
          │
          ▼
  مستوردات محلية في المتصفح
          │
          ▼
Schedule + Calendar + WBS + ResourceAssignments
          │
          ├──► CPM / TIA / Windows / Concurrency / Narrative
          ├──► اختيار موارد الأنشطة المتأثرة → Financial Exposure
          └──► Event → Evidence → Notice Draft → Claim Review → DOCX/PDF

السجلات الدائمة: tRPC → Express → Drizzle → قاعدة البيانات
ملفات الأدلة: واجهة خادم محمية → تخزين كائنات S3 (بيانات وصفية فقط في القاعدة)
```

## 4. نموذج البيانات

الجدول الزمني نفسه ينشأ في المتصفح ويمكن حفظه كـ JSON. أما البيانات التي يجب أن تبقى قابلة للتدقيق فتسجل في قاعدة البيانات. لا تحفظ بايتات ملفات الأدلة في قاعدة البيانات؛ تحفظ مفاتيح التخزين والبيانات الوصفية فقط.

| الجدول | المفتاح التشغيلي | أهم الحقول | سبب وجوده |
|---|---|---|---|
| `users` | حساب OAuth | الاسم والبريد والدور | تحديد الفاعل والصلاحيات |
| `evidence_documents` | مشروع + حدث + مستخدم | النوع والملف ورابط التخزين والوصف | ربط مستند الدليل بحدث |
| `resource_assignments` | مشروع + Assignment Key | النشاط والمورد والكمية والتكلفة والنوع | لقطة قابلة للتتبع من P6 |
| `notice_register` | مشروع + رقم Notice | الحدث والمواعيد والحالة والسرد والأثر والأدلة | سجل Notice غير المرسل تلقائياً |
| `claim_reviews` | مشروع + Claim Key | المرحلة والحالة والمالك | الحالة الحية لمسار المطالبة |
| `claim_review_stages` | Claim Review | المراجع والقرار والتعليق والتاريخ | سجل تدقيق إضافي غير قابل للتعديل من الواجهة |
| `claim_review_participants` | Claim Review + Stage | المراجع المعين ومن عيّنه | حد الصلاحية لكل بوابة مراجعة |

## 5. منطق CPM وTIA خطوة بخطوة

1. **تحقق المدخلات:** يفحص المحرك تكرار معرفات الأنشطة والعلاقات غير الموجودة والحلقات المنطقية.
2. **التقويم:** يحول مدد أيام العمل إلى تواريخ مع مراعاة أيام العمل والعطل.
3. **التمرير الأمامي:** يحسب ES وEF لكل نشاط وفق نوع العلاقة وLag.
4. **التمرير الخلفي:** يحسب LS وLF ثم العائمة الكلية.
5. **المسار الحرج:** يميز الأنشطة ذات العائمة الصفرية أو ضمن هامش الدقة المحدد.
6. **خط الأساس:** يحسب تاريخ الإكمال قبل إدراج الحدث.
7. **Fragnet:** يستبدل العلاقة المختارة بنشاط/أنشطة الحدث وعلاقات الدخول والخروج.
8. **حالة الأثر:** يعيد حساب الشبكة ويقارن الإكمال الجديد بالأساس. الفرق هو أثر النموذج الزمني، لا قرار الاستحقاق.
9. **النوافذ والتزامن:** يحلل الحدث داخل نافذة تاريخية ويسجل مؤشرات التزامن للمراجعة الفنية.
10. **السرد:** يولد نصاً عربياً يذكر نطاق التحليل والمدد والمسار والتحفظات.

## 6. الموارد والأثر المالي

يقرأ المستورد جدول `TASKRSRC` من XER أو مكافئه في XML. تشمل الحقول المهمة `task_id` و`rsrc_id` و`rsrc_type` و`target_cost` و`remain_cost` و`act_reg_cost` و`act_ot_cost` و`target_qty` و`remain_qty` و`act_reg_qty` و`act_ot_qty` و`cost_per_qty` و`acct_id` و`wbs_id` [3].

لا يجمع التطبيق كل موارد المشروع عند وجود حدث محدد. يختار إسنادات الأنشطة التي يلمسها الـ Fragnet، بما في ذلك نقاط الاتصال مع برنامج الأساس، ثم يحسب:

```text
تكلفة المورد اليومية = معدل تكلفة الوحدة × كمية المورد اليومية
تعرض التمديد = مجموع التكلفة اليومية للموارد في نطاق الحدث × أيام الأثر الزمني
```

يفصل العرض بين العمالة، والموارد غير العمالية، والمواد، ويرفع تحذيراً عندما لا تتطابق معرفات النشاط أو تنقص تكلفة/كمية لازمة. لا تخلط هذه المعادلة التكلفة المخططة والفعليـة والمتبقية في رقم واحد غير مبرر؛ تحفظ الحقول الأصلية منفصلة كي يراجعها محلل التكلفة.

## 7. Workflow تشغيلي مقترح

| البوابة | الإجراء | نقطة التحقق الداخلية | المخرج قبل الانتقال |
|---|---|---|---|
| 1. الاستلام | استورد XER أو XML أو JSON | عدد الأنشطة والعلاقات، عدم وجود حلقات، التقويم | برنامج قابل للحساب |
| 2. تجميد الأساس | راجع التاريخ والعطل والمنطق | تاريخ الإكمال الأساسي ومسار حرج ظاهر | نسخة أساس موثقة |
| 3. تعريف الحدث | أنشئ Fragnet واربطه بعلاقة قائمة | تاريخ الحدث، السبب، والارتباطات صحيحة | حدث قابل للقياس |
| 4. الحساب | شغل TIA أو نافذة | مقارنة قبل/بعد، تزامن، وعائمة | نتيجة أيام قابلة للمراجعة |
| 5. الأدلة | أرفق وأصنف المستندات | كل دليل له حدث ونوع ووصف | سجل أدلة قابل للتتبع |
| 6. التكلفة | راجع الموارد في نطاق الحدث | لا تحذيرات مطابقة حرجة أو عالجها | تعرض مالي تخطيطي |
| 7. Notice | أنشئ مسودة وعدّل بيانات العقد | تاريخ العلم والاستحقاق والبند والأدلة | Notice محفوظ للمراجعة |
| 8. الاعتماد | أحل المطالبة للمراحل | مراجع معين لكل بوابة وسجل قرار | جاهزة للتصدير أو مرفوضة |
| 9. التقرير | صدّر DOCX/PDF | السرد والنتيجة والماليات والإشعارات والاعتماد | حزمة عرض للمراجعة البشرية |

## 8. إعادة بناء التطبيق من الصفر

ابدأ من مشروع React + TypeScript، ثم أنشئ طبقة خادم Express وtRPC وDrizzle. عرّف مخطط القاعدة أولاً، ثم نفذ الترحيل بالمبدأ: **تغيير المخطط → توليد SQL → مراجعة SQL → تطبيقه → اختبار الاستعلام**. بعد ذلك اكتب محرك CPM كوحدة نقية لا تعتمد على DOM، واكتب المستوردات لتنتج نموذج Schedule نفسه. هذا الفصل هو ما يتيح اختبار الحساب واستيراد الملفات دون واجهة.

### تسلسل بناء موصى به

1. نماذج `Activity` و`Relationship` و`Calendar` و`Schedule` و`Fragnet`.
2. فاحص شبكة واتجاه طوبولوجي وتمرير أمامي/خلفي.
3. مستورد JSON ثم CSV، وبعد ثبات النموذج أضف XER وP6 XML.
4. TIA بإدراج Fragnet غير مدمر في نسخة من برنامج الأساس.
5. نوافذ وتزامن وسرد فني.
6. قاعدة بيانات للأدلة والموارد وNotices والمراجعة.
7. واجهات tRPC محمية لكل عملية تعديل، مع عزل السجل حسب المستخدم/المشروع.
8. DOCX/PDF واختبارات وحدة وتدفق كامل.

## 9. قواعد الاختبار والجودة

تشمل الاختبارات الآلية محرك CPM، التقاويم، التزامن، XER/XML، الموارد، الأثر المالي، التصدير، Notice الآلي، صلاحيات المراجعة، ومسار مطالبة كامل. شغّل الأمر التالي قبل كل حفظ أو نشر:

```bash
pnpm test
```

لا يكفي نجاح الاختبار الآلي وحده. راجع بصرياً على سطح المكتب والهاتف، وحمّل ملف P6 حقيقياً من بيئة مشروع تجريبية، ثم راجع تقرير DOCX/PDF مع مخطط وعقود قبل أي استخدام تعاقدي.

## 10. الأمان وحدود المسؤولية

تعمل حسابات CPM وTIA واستيراد P6 والحساب المالي داخل المتصفح. لكن رفع الأدلة والسجل المستمر وNotices والاعتماد تستخدم حساباً مسجلاً وخادماً وقاعدة بيانات. لا توجد في النسخة الحالية مكالمة نموذج لغوي أو خدمة ذكاء اصطناعي لإنتاج الحسابات أو السرد؛ السرد قالب حسابي مبني على النتيجة. لذلك لا تُرسل بيانات البرنامج إلى خوارزمية ذكاء اصطناعي خارجية بواسطة هذه الوظائف.

أي تحليل أو Notice أو تقرير يتطلب مراجعة المسؤول المخول وفريق التخطيط والعقود. يمثل التطبيق أداة تنظيم وتحليل قابلة للتتبع، ولا يعد بديلاً عن العقد أو الإشعار الرسمي أو الرأي القانوني.
